# Decisions

Section 1 of the execution plan asks that any scientific change be recorded
here before results are inspected. This file is that record. It covers the
choices a reader cannot recover from the code alone: where the plan left a
choice open, where it named something this run could not do, and where the
data made a predeclared setting uninformative.

Engineering-only changes — file names, caching, bug fixes that change no
reported number — are in the commit history, not here. Where a decision changed
a number that appears in the report, the effect is stated.

Format of each entry: what the plan said, what was done, why, and what it costs
the result.

---

## D1. Core-8 for development, Core-20 for every reported number

**Plan.** Section 10 fixes the Core-20 judge table; section 10.3 prescribes
Core-8 as the smoke panel.

**Done.** Core-8 was used only to prove the pipeline end to end and to pass the
G0-G2 gates the first time. Every number in `FINAL_REPORT.md`, every figure and
every table is from the full Core-20 panel. All 20 judges were scored; nothing
is extrapolated from the 8.

**Why.** Core-8 exists to find bugs cheaply, not to answer claims. Section 31's
error band is stated for Core-20, so reporting a Core-8 frontier against it
would compare two different objects.

**Cost.** None to the claims. The Core-8 results stay in `results/` so the two
panels can be compared, but they are never mixed into a Core-20 table.

---

## D2. J07 was gated, then ungated, and the panel is complete

**Plan.** Section 10's table names 20 judges.

**Done.** J07's weights were gated on Hugging Face and the first full run went
ahead on 19 judges rather than wait. Access was granted later and J07 was
scored, so the reported panel is all 20. The 19-judge run is kept in
`results/archive_19judge/` for comparison and `docs/PANEL_19_VS_20.md` records
what the twentieth judge changed.

**Why.** Waiting on an access request would have blocked every downstream
experiment. Running short and saying so was preferable to substituting a judge
that is not in the plan's table.

**Cost.** None now. While it stood, the deviation was named in the report
rather than hidden, and the output files kept the registry name `core20`
throughout so no reader has to reconcile two naming schemes.

---

## D3. One inference pass pays for everything else

**Plan.** Section 42 budgets the compute; sections 13 and 14 fix the benchmark
and the pair construction.

**Done.** The reported grid is 20 judges by 7 contexts by 3724 comparison pairs
— about 521,000 scored prompts — produced in a single pass on rented GPU time
and cached. Every experiment after that reads the cache and runs on CPU.

**Why.** The scoring pass is the only expensive step in the project, and on a
student budget it could be afforded once. Fixing that early makes the later
trade-offs explicit rather than discovering them one at a time.

**Cost.** Three limitations in this file follow directly from it, and each is
named where it bites: bands are over split seeds and not inference seeds (D7),
E7 transfers to one benchmark and not two (D17), and E8 was not run (D16).
Anything that would have required re-querying the judges was not done.

---

## D4. Ties are a third class, not a discarded case

**Plan.** Section 7 defines the loss on the three-class simplex; section 14.2
requires tie tasks to be retained with label C.

**Done.** Judges emit a distribution over A-better, B-better and tie, and the
coverage error is total variation on that simplex. Tie tasks are kept and carry
a real target, rather than being dropped or folded into a binary preference.

**Why.** A panel that is compressed on binary preferences can silently lose the
ability to abstain, which is exactly the behaviour a governance reader cares
about. Tie bias is also one of the behaviours the judge-behaviour notebook
reports.

**Cost.** Every fit is a three-column problem instead of a scalar one, which is
what forced the coverage layer to be generalised. JudgeBench contains no ties,
so E7 says nothing about whether the tie corner transfers (see D17).

---

## D5. Judge output is a restricted softmax over label tokens, never sampled

**Plan.** Section 12 requires deterministic probability extraction.

**Done.** For each rendered prompt the three label continuations are scored by
sequence log-likelihood and turned into a distribution by a softmax restricted
to those three candidates. The main matrix is never generated by sampling.
`audit_tokenization` records the token encoding for every model and refuses to
proceed when the label boundary convention is inconsistent between models.

**Why.** Sampled verdicts would make the whole tensor a random variable and
every downstream error a sampling artefact at some unknown rate. A restricted
softmax is deterministic given the weights and gives a genuine distribution
rather than a one-hot label, which the three-class geometry needs.

**Cost.** The numbers describe how the judge scores the three labels, not what
it would have written if asked to answer freely. Those can differ, and this
project measures the first.

---

## D6. Splits are grouped at the base task and are 50/25/25

**Plan.** Section 15 requires grouped, stratified FIT / CERT / TEST splits at
50/25/25.

**Done.** Assignment happens at the base-task level: every pair, orientation
and intervention derived from one task lands in the same split. Strata are
domain crossed with tie status. Each split manifest carries a SHA-256 over its
item ids and the hash of every prompt template.

**Why.** Splitting at the rendered-prompt level would put one orientation of a
pair in FIT and the other in TEST, and the held-out error would then be read
partly off items the fit already saw.

**Cost.** Fewer effective TEST items than a prompt-level split would report,
which is the honest count.

---

## D7. Bands are over split seeds, not over inference seeds

**Plan.** Section 34 asks for uncertainty across seeds.

**Done.** Five predeclared split seeds re-partition one cached set of judge
responses. The pairs seed, which fixes what each judge was actually asked, is
held at its primary value.

**Why.** Re-querying 20 judges across 7 contexts for each of five seeds was not
affordable on the available GPU time.

**Cost.** This is the largest limitation in the package and is named as a
deviation in the report. The bands cover partition variance only. They do not
cover variance in the judges' own outputs, so they are narrower than a full
resampling band would be and should not be read as one.

---

## D8. The reconstruction rule is simplex-constrained

**Plan.** Section 7 defines the virtual judge as a convex combination, so its
weights belong on the simplex.

**Done.** The primary rule keeps weights on the simplex. Unconstrained,
non-negative and ridge rules are computed and reported beside it as
diagnostics.

**Why.** The unconstrained rules score lower total variation, but their output
leaves the simplex on up to 95% of items. Such an output is not a probability
distribution and cannot be shipped as a judge verdict, so a frontier built on
it would not describe anything deployable.

**Cost.** The headline error is higher than the best achievable number in the
rule table. That comparison is reported explicitly, with the off-simplex
fraction beside it, so the trade is visible rather than assumed.

---

## D9. The headline is the worst judge in its worst context

**Plan.** Section 7 defines the coverage functional as a maximum over judges,
and section 14.3 makes it a maximum over registered contexts.

**Done.** Every verdict is stated on the worst-judge worst-context mean total
variation. Mean-judge, median-item and 95th-percentile errors are reported in
the same tables but never used as the headline.

**Why.** The claims are about every judge being preserved. A mean would let one
badly reconstructed specialist be paid for by nineteen easy ones.

**Cost.** C2 comes back UNSUPPORTED on this panel. On the mean-judge column the
same run would look far better. The report says so in the C2 section rather
than quietly changing the statistic.

---

## D10. Minimax weights are solved by cutting planes, with the exact LP as a test reference

**Plan.** Section 17.1 prescribes the robust fit as one linear program with a
slack variable per item, solved by HiGHS through SciPy. Section 17.2 permits
accelerations and forbids reporting a heuristic estimate as an exact
certificate.

**Done.** `solve_minimax_weights` is a Kelley cutting-plane loop, which solves
the same program by adding supporting hyperplanes instead of carrying every
per-item slack. The monolithic LP of section 17.1 survives as
`solve_minimax_weights_lp` and the tests assert the two agree. A deterministic
tie-break is applied because the minimax argmin is not unique.

**Why.** The monolithic LP was about 1450 times slower at 20 judges, which made
the seed sweeps unaffordable. This is an acceleration in the sense of section
17.2 and not a surrogate: the master program bounds the objective from below,
the best evaluated iterate bounds it from above, and the loop exits when that
interval closes, so the returned value is exact at convergence rather than
estimated. The tie-break exists so that two runs of the same configuration
return the same weights; without it the reported panel could change between
runs for no scientific reason.

**Cost.** One residual slack is accepted rather than raised. If the iteration
limit is reached with the interval still open by no more than 1e-5, the best
iterate is returned with a warning; a wider gap still raises. The returned
number is an error the returned weights actually achieve, so the slack only
bounds how far it sits above the optimum, and it is two orders below the four
decimals anything reported carries. The guard exists because a Core-20 run
aborted three hours in on a gap that printed identically to the tolerance.

---

## D11. Minimum feasible size is a bound when enumeration is out of reach

**Plan.** Section 22 asks for the minimum feasible set alongside the naive one.

**Done.** Where the panel is small enough, the minimum is certified by pruned
exhaustive enumeration. Where it is not, the reported value is backward
elimination's upper bound, labelled as such, and the certified lower bound is
carried in the same record.

**Why.** Enumerating every subset of 20 judges at every tolerance is not
affordable, and E0's evaluation budget is finite. Monotonicity of the coverage
error licenses the pruning that makes the small cases exact.

**Cost.** In 90 of 95 E0 cases the composition gap is an upper bound rather
than an exact figure. C1 does not rest on it: the 86 violations that carry the
claim are single coverage evaluations and are exact in every case. The report
states this in the C1 section.

---

## D12. The tolerance grid is extended, and the predeclared points are reported empty

**Plan.** Section 23 predeclares the tolerance grid and allows it to be
extended provided those points remain.

**Done.** The section 23 values are reported. On these judges every one of them
selects the whole panel, so the grid is extended upward to the range where the
answer changes, and the informative tolerances are additionally taken from the
sorted leave-one-out errors, which is where the removable set can change at all.

**Why.** Reporting only a grid on which nothing happens would hide the result
rather than test it. Widening quietly would be worse: the predeclared points
are kept and shown as empty so a reader can see that the grid was vacuous here
and not that it was replaced.

**Cost.** Tolerances outside the predeclared grid are data-driven and are
labelled that way everywhere they appear. The C1 headline is quoted at the
predeclared value 0.20, not at a data-driven one.

---

## D13. C3 is decided by a paired bootstrap, not by overlapping intervals

**Plan.** Section 34.2 specifies paired comparison on shared cells.

**Done.** Coverage is compared to each baseline cell by cell, on the same
budget and the same split seed, and the interval is over the paired difference.
Marginal intervals are reported too but do not decide anything.

**Why.** Two methods evaluated on the same splits are not independent samples.
Reading overlap between their marginal intervals understates a real and
consistent difference.

**Cost.** None. The paired result is the stronger one here, and the cells where
coverage loses are reported with their budget range attached rather than
averaged away.

---

## D14. The luckiest random draw and the rank-k floor are references, not competitors

**Plan.** Section 21 lists random selection among the baselines.

**Done.** Plain random selection is reported as a baseline. The best of 100
random panels, chosen after seeing which one won, is reported separately and
labelled an oracle. The rank-k floor is reported as a reference for how much of
the error is dimensional.

**Why.** No practitioner can produce the luckiest draw, so scoring it as a
competitor would flatter the baselines. The rank-k floor is not a certified
lower bound: its basis is fitted on FIT, scored on held-out rows, and chosen to
minimise squared error rather than worst-judge total variation, and it rises at
two budgets, which a true floor could not do.

**Cost.** None, provided both keep their labels. The report states the
non-bound status in the same table where the floor appears.

---

## D15. The backbone is enumerated, not read off one greedy run

**Plan.** Section 20 requires the mandatory analysis of which judges are
structurally necessary.

**Done.** For each tolerance and each split seed, the optimal sets are
enumerated with monotone pruning, and a judge is called mandatory only if it
appears in every optimum, optional if it appears in some, nonessential if it
appears in none, and unstable if that category changes with the split seed.

**Why.** A judge that a greedy run happens to keep is not thereby necessary.
The four categories are only meaningful against the set of optima, so they are
computed against it. The optional category is the one the question is actually
about and cannot be recovered by subtraction from the two extremes.

**Cost.** The analysis is limited to the tolerances where enumeration
completes. Judges whose category varies by seed are reported as unstable rather
than quoted as a finding.

---

## D16. Sparsity is enforced exactly, and cost is reported even though it does not separate

**Plan.** Section 28 defines the sparse and cost-aware variants. Section 30
marks E8 as theory support that should not delay the paper.

**Done.** A support cap of r is enforced by enumerating supports of size r, not
by an L1 surrogate. Three cost objectives are reported: measured inference
seconds, memory, and distinct model families. E8 was not run.

**Why.** An L1 surrogate would give a sparse-ish answer whose support size is
not the constrained quantity, and the claim is about the constrained quantity.
The cost objectives are reported in full even though seconds and memory always
return the same panel as plain judge count, because these judges are close to
uniform in runtime and parameter count; only distinct model families ever
disagrees, at two tolerances. That is a negative result about this panel and is
reported as one.

**Cost.** C8 is PARTIALLY SUPPORTED: the sparsity half holds, the cost half
does not separate. E8's absence is recorded in the compliance section.

---

## D17. E7 transfers to JudgeBench only

**Plan.** Section 29 names JudgeBench and JuStRank as the transfer benchmarks
and lists three settings.

**Done.** All three settings are implemented — frozen basis with frozen
weights, frozen basis with refitted weights on a calibration sample, and oracle
reselection as a diagnostic. Only JudgeBench is used.

**Why.** Each additional transfer benchmark is another full scoring pass over
20 judges and 7 contexts on rented GPU time. One transfer benchmark answers the
question the claim is stated over; two would strengthen it but were not
affordable within the course.

**Cost.** Transfer is demonstrated on one shift, not two. JudgeBench also
contains no ties, so nothing in E7 says whether the tie corner of the simplex
transfers. Both limits are stated in the E7 section.

---

## D18. Nothing is substituted for a number that was not produced

**Plan.** Sections 65 and 66 fix the archive contents and the report structure.

**Done.** A section whose input file does not exist prints "Not run" and stops.
Verdicts use only the four tokens section 66 allows, and the token at the top
of each claim is extracted from that claim's own prose rather than declared
beside it. `RESULT_INDEX.json` is generated from the same section bodies, and a
test asserts the index and the report agree claim by claim.

**Why.** A report whose headline can disagree with the argument underneath it
is the failure mode this structure exists to prevent. Generating both documents
from one set of section builders makes the disagreement impossible rather than
merely unlikely.

**Cost.** The report is longer and more hedged than a hand-written one. Every
open gap is named in the compliance section instead of being absent.
